Zuriauto Release Test Run

Every module, in the order that finds problems soonest and does the least damage when it finds one. Run all of it against a preview deployment, never against zuriauto.ch.

Before you start

Five things to have open. If you cannot fill in all five, stop at Part 1 — everything after it needs them.

PREVIEW_URL
The Vercel preview for integrate/backend-plus-return. Not the production domain.
APPLY_SECRET
Signs the returning-customer document-reuse token. No longer opens or fences anything.
ADMIN_SECRET
The fleet page key. Must be a different value from APPLY_SECRET.
CRON_SECRET
Bearer token for the daily run.
psql
A connection to the preview Neon branch, for the verification queries.

Use your own email address wherever a renter's address is asked for. Several steps send real mail, and one of them cannot be undone.

Set the Preview environment variables first All eleven keys, in Vercel's Preview environment, not just Production. A preview missing DATABASE_URL fails in a way that looks like a code bug — which is the exact confusion /api/health exists to end.
Deployment Protection breaks every curl step — read this before running any

The preview sits behind Vercel Authentication, so an unauthenticated request is answered with 302 to vercel.com/sso-api and never reaches the application. In a browser you are already signed in and see the real page, which makes this easy to miss: a curl fence check would report 302 where you expected 401, and a passing-looking result would mean nothing.

It also means the cron cannot be triggered at all — and Vercel Cron does not fire on preview deployments, so a manual trigger is the only way to exercise Part 5.

Fix it once, in Settings → Deployment Protection → Protection Bypass for Automation. Generate the secret, then send it with every request: 

export BYPASS="<VERCEL_AUTOMATION_BYPASS_SECRET>"
curl -s -H "x-vercel-protection-bypass: $BYPASS" $PREVIEW_URL/api/health/ | jq

Add that header to every curl in this guide. Prefer the bypass token over switching protection off: while you are testing, the preview writes real ID scans into the EU bucket and its pickup form would otherwise be open to anyone with the URL.

Part 0 — On your machine

Two minutes, no deployment involved. If this is red, nothing further is worth trying.

0.1

The suites

pnpm install
pnpm test                    # unit — no services needed
pnpm db:up && pnpm test:db   # needs Docker running
pnpm build
Expect 32 test files, 314 tests passing, and a clean build. This was green as of the last commit on the branch.

If pnpm db:up hangs, Docker Desktop is not running. The db suite shares one database and truncates between tests, so it is not parallelised and takes about 50 seconds.

Part 1 — Does the preview see anything?

Before testing behaviour, establish that the deployment has a database, a bucket and its secrets. Every later failure is ambiguous until this passes.

1.1

Ask the function what it can see

curl -s $PREVIEW_URL/api/health/ | jq
Expect Every variable reporting true, and the database check reporting a successful round trip. It reports presence only, never values — nothing here is a secret.

A false tells you exactly which variable is missing from the Preview environment. Fix it and redeploy before going on; the next eight steps will all fail confusingly otherwise.

1.2

Seed the fleet

DATABASE_URL="<preview neon url>" pnpm exec prisma migrate deploy
DATABASE_URL="<preview neon url>" pnpm db:seed
Expect Three migrations applied, then SELECT count(*) FROM "Car"; returning 9 — including the BMW 218d, ZH 656 404.
Never migrate dev prisma migrate dev can offer to reset the database. Against anything with data in it that is unrecoverable. Always migrate deploy.
1.3

The picker reads the table

curl -s $PREVIEW_URL/api/fleet/ | jq '.vehicles | length'
Expect 9. Now retire one in the database and call it again — it should return 8 without a deploy. Put it back to available afterwards.
1.4

The write fence holds

curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST $PREVIEW_URL/api/rental-contract/
Expect 401. An unfenced pickup endpoint would let anyone create a rental naming a real driver against a real plate.
1.5

The form opens, with nothing after the URL

Open $PREVIEW_URL/pickup/.

Expect The five-step wizard. There is no gate any more — APPLY_SECRET stopped fencing this route deliberately, so the office can hand out a bare link. Also check /apply/?k=… still lands on the form: links already circulated keep working, and the stale key is ignored rather than refused.
What protects it now An origin check, a honeypot and the per-address rate limiter on the write endpoint — the same set /return/ has always run on alone. Anyone who can load this page can submit to it.

Part 2 — One rental, all the way through

The core path. Pick a car you can take out of service afterwards and use your own email as the renter.

2.1

Sign a pickup contract

Complete the wizard at /pickup/: choose a car, photograph an ID and a licence (any document will do on preview), take a portrait, enter weekly terms, sign, submit.

Expect
  • The PDF arrives by email, with a correct terms block.
  • The number reads ZA-YYYYMMDD-0001 — a real sequence, not a random suffix.
  • Seven objects plus the PDF sit under one pickup/<uuid>/ prefix in R2.
SELECT "contractNumber", "mailSentAt", "mailError" FROM "Contract";
SELECT status FROM "Car" WHERE plate = 'ZH …';   -- rented
SELECT count(*) FROM "Charge";                    -- one per week
2.2

The car leaves the picker

curl -s $PREVIEW_URL/api/fleet/ | jq '.vehicles[].plate'
Expect The plate you just rented is gone. A customer must never be able to sign a contract naming a car somebody is driving.
2.3

Recognise the returning customer

Start a second pickup for a different car. At the desk step, look the renter up by the phone number you used in 2.1 — try a different spelling of it, for example +41 79 … against the 079 … you typed first.

Expect The customer is found despite the different spelling, their documents are offered, and taking them skips the photography steps. The PDF prints a reference page naming the contract they came from. 
SELECT "documentsReusedFromId", "identityCheckedAt" FROM "Contract"
  WHERE kind = 'PICKUP' ORDER BY "signedAt" DESC LIMIT 1;
-- both non-null on the second contract

SELECT count(*) FROM "CustomerLookup";  -- the lookup is audited

Documents are copied, not shared, so the second contract owns its own set of objects on its own retention clock. Expect five new objects in the bucket, not five references to the old ones.

Part 3 — The return

New in Phase 4, and the part with the least production history. The form is public: no key, opened by the renter.

3.1

Submit a return

Open $PREVIEW_URL/return/ — no key — and complete it for the car from 2.1. Enter a mileage higher than the pickup reading, answer the condition and payment questions, sign, submit.

Expect The signed report arrives by email. The office copy ends with RECORDED — confirm it in /admin to free the car. and the distance driven. 
SELECT kind, "contractNumber", "mileageKm", "fuelLevel"
  FROM "Contract" WHERE kind = 'RETURN_ADDENDUM';

SELECT status FROM "Rental";                     -- RETURN_SUBMITTED
SELECT status FROM "Car" WHERE plate = 'ZH …';   -- still rented
3.2

The car is still not bookable

curl -s $PREVIEW_URL/api/fleet/ | jq '.vehicles[].plate'
Expect The plate is still absent. This is the point of the design: an unfenced form must not be able to put a car somebody may still be driving back into the picker.
3.3

The three flags the office relies on

Submit three more returns on other rentals and check the office email each time.

Do thisThe office copy should say
A mileage lower than the pickup readingCHECK: the reading is BELOW the pickup mileage — recorded anyway, because the document is already signed
An email that differs from the one on fileCHECK: the submitted email does not match the customer on file — still recorded, since a renter may simply have changed address
A car with no open rentalNOT RECORDED — no open rental was found for this car — and the report still arrives
3.4

A second return is refused, not duplicated

Submit the return form again for the same car.

Expect NOT RECORDED — a return is already on file for this rental. and exactly one RETURN_ADDENDUM row, not two.

Part 4 — The fleet page

/admin is unlinked and noindex; the secret is what protects it.

4.1

Everything refuses without the secret

curl -s -o /dev/null -w '%{http_code}\n' $PREVIEW_URL/api/admin/overview/
curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST $PREVIEW_URL/api/admin/session/ \
  -H 'content-type: application/json' -d '{"secret":"wrong"}'
Expect 401 from both. A wrong secret, a missing one and an unconfigured server all give the same answer on purpose.
Check this by hand Confirm ADMIN_SECRET and APPLY_SECRET are different values in Vercel. The pickup key is pasted into WhatsApp and leaks on the first forward; the admin key can rewrite the fleet.
4.2

Sign in and read the board

Open $PREVIEW_URL/admin in a browser and enter the admin secret.

Expect A twelve-hour session. The counters read: 9 cars, the rentals you created, and Rückgabe offen: 1 from Part 3. The returned rental sits at the top of the list badged Zurückgegeben – bestätigen, showing the return date and its ZR- number.
4.3

Confirm the return — the one click

Press the confirm button on that rental.

Expect
  • The rental reads COMPLETED.
  • The car reads available.
  • The plate is back in /api/fleet/.
  • Rückgabe offen falls to 0.

Both rows move in one transaction. Half of it — a freed car whose rental is still active — is the state that lets the picker offer a car somebody is driving.

4.4

Add, edit, retire

Add a car with a made-up plate. Edit its model. Retire it. Check /api/fleet/ after each.

Expect The new car appears in the picker while available and vanishes when retired — with no deploy. Its slug is derived from the model and plate; check a name with an umlaut (Škoda) survives intact.

Part 5 — The daily run

This is where real email goes to real inboxes. It is last for that reason.

5.1

The trigger is closed to everyone else

curl -s -o /dev/null -w '%{http_code}\n' $PREVIEW_URL/api/cron/daily/
Expect 401. This endpoint sends mail to real customers; an open trigger is not acceptable.
5.2

Run it, then run it again

curl -s -H "Authorization: Bearer $CRON_SECRET" \
  $PREVIEW_URL/api/cron/daily/ | jq

# immediately again
curl -s -H "Authorization: Bearer $CRON_SECRET" \
  $PREVIEW_URL/api/cron/daily/ | jq
Expect {"ok":true,…} both times, and the second run all zeros. Idempotence is claimed by inserting the notification row before sending, so a second run finds the decision already made.
5.3

One real reminder

Move a test rental's end date to about 36 hours out, then trigger the cron.

UPDATE "Rental" SET "endAt" = now() + interval '36 hours'
  WHERE id = '…';
Expect reminded: 1, and an email that arrives in the language the contract was signed in — not the browser's language — carrying a working manage link.
The step most likely to fail, and the only one that cannot be undone SMTP from a serverless function has failed in this project before, and a sent email does not roll back. Use your own address. If it fails, the failure is recorded on the notification row rather than lost — check error and attempts.
5.4

Extend from the link

Open the manage link from that email (/rental/manage?t=…) and take the extension.

Expect A confirmation email, an office copy, a new endAt, and new Charge rows continuing the week numbering rather than restarting it. Then open the same link again and expect the “link no longer valid” page — the token is single use. 
SELECT kind, "sentAt", error FROM "Notification";  -- all sent, no errors
SELECT "weekNumber", status FROM "Charge" ORDER BY "weekNumber";
5.5

A returned car still owes its money

On a rental sitting in RETURN_SUBMITTED with an unpaid week, run the cron.

Expect The charge is still requested. Submitting the return form must not switch off a renter's own payment reminders — this was a real hole found while building Phase 4 and is now covered by a test.

Part 6 — Clean up

Leave the preview database empty, so the next run starts from the same place this one did.

6.1

Remove the test data

Delete the test rentals, their contracts, charges, notifications and tokens; set the cars back to available; delete the objects from R2 under the pickup/ prefixes you created.

Only on preview If any of this ever runs against the production database, the contracts it deletes are commercial records with a ten-year retention obligation under OR 958f.

When something fails

The failures this system produces are mostly quiet by design, so the symptom rarely names the cause.

SymptomAlmost always
500 in a few milliseconds, no outgoing requestDATABASE_URL missing — not a rejected password. Check /api/health/.
Uploads fail with NoSuchBucketThe EU bucket addressed on the plain R2 host. A jurisdiction-pinned bucket answers only on <account>.eu.r2.cloudflarestorage.com.
The customer gets a PDF but no row appearsDATABASE_URL or R2_BUCKET missing: the write answers 503 and the wizard falls back to the Phase 1 download — silently, by design. A missing APPLY_SECRET is no longer a cause; it only breaks document reuse.
Build fails on vercel.jsonA comment key. Vercel's schema rejects unknown properties outright.
Cron never fires on its ownCron only runs on production deployments of the default branch. Trigger previews by hand with the bearer token.
The app refuses to startR2_BUCKET unset in production. Deliberate: discarding ID scans while reporting success is the worse failure.
A returning customer is never foundTheir phoneKey predates the normaliser. Run pnpm db:backfill-phone-keys.
