Where the work actually sits

The branch is a complete implementation of Phases 2 and 3 plus two features that arrived after them. What it is not is a tested one — Vercel has never built this code, so no line of it has met a real database, a real bucket, or a real mail server.

The last commit Vercel has ever seen is 8fffd81, from 22 August. Everything after it — the whole of returning-customer recognition and the whole of the /admin fleet dashboard — exists only on this machine. That single fact is what separates “the code is written” from “we can release.”

Two pieces of good news from the same check: the merge into main is clean — no conflicts, including in lib/rental/fleet.ts, which both sides touched — and the design decisions below are documented in the source itself, at a density that made this register possible to write without guessing.

Foundation

The two stores everything else writes into, and the reasons each is shaped the way it is.

Built, unproven
prisma/schema.prismaprisma/migrations/ ×3lib/db.ts

Postgres and the Prisma layer

Twelve models across three migrations: Organisation, Car, Customer, Rental, Contract, Asset, RentalEvent, Charge, Notification, ActionToken, plus two audit tables. Every table carries an organisation key from the first migration.

The tenant key is there before there is a second tenant on purpose. Retrofitting it later means rewriting every query and every access check; carrying an unused column costs nothing.

The client is created on first use, not at import. A Prisma client built at module scope against a missing DATABASE_URL fails later, at the first query, with an error describing the symptom rather than the cause — which is exactly the failure that wasted an afternoon on a preview deploy.

Built, unproven
lib/storage/r2.tslib/storage/keys.tslib/storage/memory.ts

The asset store, pinned to the EU

Cloudflare R2 over its S3-compatible API, holding ID scans, driving licences, portraits, signatures, condition photographs and the contract PDF itself. R2 rather than Vercel Blob for one reason: a bucket's jurisdiction can be fixed to the EU at creation, which the revised Swiss DSG makes a requirement rather than a preference for this data.

A jurisdiction-restricted bucket does not answer on the account's ordinary host — it has its own, <account>.eu.r2.cloudflarestorage.com. Address the plain one and every upload fails with NoSuchBucket, which surfaces as a 503 and a contract that was signed and never recorded. The code defaults to the EU host for that reason.

Object keys are deliberately meaningless: pickup/<uuid>/<kind>-<random>.jpg, carrying no name, email or contract number. A key ends up in server logs, in the storage console, and in whatever support ticket somebody pastes it into — putting a name in one leaks the link between a person and their passport scan to everywhere a string can travel.

Pickup, recorded — Phase 2

What used to be a form that emailed a PDF is now a write to a system of record. The email still goes; it is no longer the only copy.

Built, unproven
lib/rental/persistPickup.tsapp/api/rental-contract/route.ts

One handover, three ordered stages

Assets upload first, the database transaction opens second, the mail sends last — the durable write sits in the middle, where it belongs. A storage failure aborts before anything is written. A mail failure leaves the contract standing and records mailError on the row.

This inverts the Phase 1 failure mode, where the email was the record, so a failed send meant the contract existed nowhere at all.

Built, unproven
lib/rental/contractNumber.ts

A real contract sequence

ZA-YYYYMMDD-NNNN, allocated from a counter row per organisation per day with a single ON CONFLICT DO UPDATE … RETURNING statement, taken inside the contract transaction. Two simultaneous handovers serialise on the counter row instead of racing, and a contract that rolls back leaves no gap in the sequence.

Replaces the Phase 1 stopgap of date plus plate digits plus a random suffix. The shape is unchanged, so numbers already quoted to customers stay recognisable. The day is Zurich's day, not UTC's, and the counter pads rather than truncates — the ten-thousandth contract makes the number longer, it does not start again at one.

Built, unproven
lib/rental/terms.tscomponents/rental/RentalTermsStep.tsxlib/rental/money.ts

Rental terms, and money as integers

Two commercial shapes on one table. WEEKLY reproduces what the taxi and Uber drivers already have — N weeks at a fixed weekly amount — and FIXED_TERM serves tourists with an explicit end and a single price. Both write endAt, so the reminder pass is one indexed range scan rather than two code paths that can drift.

Every rental date is reasoned about in Europe/Zurich. Vercel's functions run in UTC; a car handed over at 10:00 for two weeks across the March changeover must still be due back at 10:00, and millisecond arithmetic would quietly make it 11:00.

Money is integer cents everywhere, never a float — the amount printed on a signed contract has to be the amount charged. The parser tolerates Swiss separators, including the typographic apostrophe iOS substitutes for a straight one, and rejects three decimals as not-an-amount.

Built, unproven
lib/applyKey.tslib/rental/rateLimit.ts

The write fence

APPLY_SECRET, compared in constant time, failing closed when unset. An open endpoint would let anyone create a rental against a real plate — and a fabricated rental naming a real driver is far worse than a spam email, because the traffic-fine lookup would answer with it.

This is an office credential, and the module says so in capitals. It is pasted into WhatsApp by staff and leaks the moment a link is forwarded. It must never fence a renter-facing flow — mailing customers this secret would hand every past renter permanent write access to the system of record.

Rate limiting moved into the database: five submissions per ten minutes, IPs stored as salted SHA-256 so the limiter is not itself a store of personal data, expired rows swept on the way past. The module-scope Map it replaced reset on every cold start and was shared between no instances at all.

Built, unproven
app/api/fleet/route.tsprisma/seed.tslib/rental/fleet.ts

The picker reads the database

/api/fleet returns only cars whose status is available, so taking a car off the road becomes a status change rather than a deploy. Ownership is split, and the split is the point: the fleet file owns identity — model, plate, chassis number, the legal identifiers printed on a signed document, which belong somewhere a mistyped update goes through code review — and the database owns status.

The seed reconciles identity on every deploy and never writes status. Practical consequence for the BMW 218d added yesterday: it is live on production right now, because today's picker still uses the compiled list — and after this release it reaches the picker only once pnpm db:seed has run.

Lifecycle automation — Phase 3

One cron run a day, six passes, every one of them safe to run twice. This is the part with the most careful thinking in it and the least production evidence behind it.

Built, unproven
lib/rental/scheduler.tslib/rental/notify.tslib/rental/passes.tsapp/api/cron/daily/route.ts

Idempotence by construction, not by flag

Two mechanisms do all the work. A send is claimed by inserting a Notification row unique on [rentalId, kind, dedupeKey] before anything is sent, so two concurrent runs race on the insert and exactly one wins. A status change is a conditional updateMany whose WHERE repeats the precondition the pure predicate just checked — the predicate may be true twice, the update can only succeed once.

The rejected alternative is named in the source: a reminderSent: boolean set after the send. Both runs read false, both send, both then set it true.

Because a claimed send that then fails to deliver must not be silently lost, delivery outcome lives in separate columns — sentAt, error, attempts — with a retry pass. The dedupe key guards the decision; the columns record the outcome.

now is threaded through every predicate rather than read from the clock, which is what lets the tests drive a rental through three weeks in milliseconds.

Built, unproven
lib/rental/passes.tsvercel.json

Why the reminder window is 48 hours

The client asked for 24 hours' notice. A daily cron firing at 09:00 and looking only 24 hours ahead would never see a rental ending at 08:00 the next morning — that end falls in the gap between two runs. Looking 48 hours ahead and deduping on the Zurich day of endAt sends the notice between 24 and 48 hours before the end, always exactly once.

The window also absorbs two facts about the free Vercel plan: cron schedules are UTC, and Hobby fires anywhere inside the hour. The alternative is an hourly cron on a paid plan, or any external scheduler pointed at the same URL with the same bearer token — the endpoint accepts POST for exactly that reason.

Built, unproven
lib/rental/actionToken.tslib/rental/manage.tsapp/rental/manage/page.tsx

Manage links for a renter with no account

Thirty-two random bytes go in the email; only their SHA-256 hash goes in the database, so a database dump does not hand over a set of live links into strangers' rental records. Single use is a usedAt stamp, revocation is deleting the row, and the token is base64url so it survives being pasted into WhatsApp. Fourteen-day life.

Chosen over a signed stateless token — an HMAC or JWT — because single use and revocation are the properties that matter here and both need a row anyway. A stateless token would buy nothing and could not be withdrawn.

Self-service extension is capped at four weeks, applied in one transaction so a new end date and its new charges land together. A renter quietly extending a car for a year should be a conversation, not a form submission.

Built, unproven
lib/payments/index.tslib/payments/sumupLink.ts

Charges, and a payment provider that admits what it is

One Charge row per week, unique on [rentalId, weekNumber] so two runs cannot create two week-three charges; extensions continue the sequence rather than restarting it. Behind a PaymentProvider interface sits exactly one implementation: the static SumUp link the site already uses.

It carries no amount and cannot report that anything was paid. Both are stated as honest limitations rather than hidden — the reminder email writes the amount in words beside the link, and the office marks the charge paid. The module explicitly refuses to append a query parameter SumUp does not read, which would make the page look parameterised when it is not.

Still an open question for the office: whether that SumUp link already offers TWINT. If it does, TWINT costs zero integration work and this is the whole payment story for a while.

Recognising a returning customer

Customers have been deduplicated on email since the first contract, so a repeat renter has always been one row with a history. Nothing read it back. This is that path — and it is the newest, least-exercised code on the branch.

Built, unproven
lib/rental/phone.tsscripts/backfill-phone-keys.ts

One spelling per phone number

A single mobile reaches the database spelled four ways — 079 123 45 67, +41 79 123 45 67, 0041791234567, +41791234567. phoneKey is the E.164 normalisation, hand-rolled rather than pulling in 150 KB of libphonenumber to serve an office typing Swiss numbers and the occasional German one.

Deliberately not unique: one mobile can belong to a couple, and a UNIQUE migration is one that can fail on data already in the table. A lookup returns up to five matches and the staff member picks.

The normaliser's output must stay stable for the life of the column. Change how an existing input maps and every key already written silently stops matching — no error, just returning customers who are never found again. A backfill script exists for when that has to happen.

Built, unproven
lib/rental/findCustomers.tsapp/api/customers/lookup/route.tslib/rental/reuseToken.ts

The desk lookup, fenced and audited

The lookup returns no image bytes and no contract id to any client. Every call writes a CustomerLookup row with the number salted and hashed, so “who looked up whom” is answerable without the audit log quietly becoming a second copy of the customer list.

What the client gets instead is a short-lived HMAC — thirty minutes, keyed with APPLY_SECRET, no database row — that authorises copying one specific contract's documents. Holding it proves the caller already legitimately read that the customer exists.

The obvious alternative, matching the submitted email against the stored one, refuses the reuse precisely when a returning customer has changed their email — which is a normal thing to have done.

Built, unproven
lib/rental/reuseDocuments.tslib/rental/contractPdf.ts

Documents carried forward, by copy

Portrait, ID front and back, licence front and back move onto the new contract — not the signature, which is signed today by definition, and not the condition photographs, which describe the car rather than the person. The copy happens server-side in the bucket, so the bytes never pass through a function and are never sent to a browser.

Copies rather than shares. Hanging one asset row off two contracts is the obvious way to reuse a file and the wrong one: it turns a per-contract deletion sweep into reference counting, and makes every retention question a question about who else still points at the object. Copying costs a few hundred kilobytes per rental and keeps each contract owning its own set on its own clock.

identityCheckedAt records the moment a staff member confirmed they had seen the original ID and licence — required whenever documents are reused, null on a first rental where the fresh photograph is itself the evidence someone looked. The PDF prints a reference page saying which contract the documents came from.

The trade-off is named in docs/DATA-RETENTION.md rather than buried: this feature is why passport and licence scans are held for five years. “It saves typing at the desk” is a weak proportionality argument under the revised DSG, and it was chosen deliberately with that written down.

Built, unproven
lib/admin/session.tsapp/api/admin/session/route.ts

A secret exchanged for a working day

ADMIN_SECRET is posted once and exchanged for an httpOnly cookie lasting twelve hours, so the office signs in each morning and the secret never travels in a URL. The cookie carries an HMAC over its own expiry, not the secret, so the stored value is not the credential and goes stale on its own.

ADMIN_SECRET must not equal APPLY_SECRET. The pickup key is pasted into WhatsApp and leaks on the first forward; the admin key can rewrite the fleet. Sharing one value would put fleet management behind a semi-public string.

A cookie here and ?k= in the pickup URL is a deliberate difference: that link is opened once from a message, this page is opened daily, and a secret in a URL accumulates in history, bookmarks and referrer headers. Accepted limitation, written down rather than discovered: one shared secret means no attribution and no per-person revocation. Rotating the variable signs everyone out, and that is the intended way to revoke.

Built, unproven
lib/admin/cars.tsapp/api/admin/cars/…app/api/admin/rentals/[id]/close/route.tscomponents/admin/AdminDashboard.tsx

Add, edit, retire — and close a rental

The office can add a car, edit it, take it off the road, see what is out on rental, and mark a returned rental finished. Closing moves both rows in one transaction: half of it — a completed rental whose car still reads rented, or a freed car whose rental is still active — is worse than neither, because the second state is what lets the picker offer a car somebody is driving.

This is labelled in its own source as an administrative override, not the return protocol. The return wizard still records mileage, fuel, damage and a signature and produces a document; this exists because until now the only way to free a returned car was hand-written SQL.

Consequence for the handover notes: step 7 of the deploy runbook is now wrong. It still tells the office that closing a rental is SQL until Phase 4. Handing them that version would be actively misleading.

Deployment plumbing

Three pieces that exist only because a deployment already went wrong once.

Built, unproven
app/api/health/route.ts

Ask the function what it can see

A health endpoint reporting presence, never values — one boolean per environment variable, grouped as the runbook lists them, plus a database round-trip that retries a cold Neon instance.

Written while diagnosing a preview where /api/fleet answered 500 in nine milliseconds with no outgoing request — the signature of a missing DATABASE_URL rather than a rejected password. Establishing that from the dashboard means reading eighteen variables across two environments and trusting the list on screen is the list the function received.

Unfenced on purpose. Every secret it names fails closed when unset, so knowing which are missing tells an attacker only that the doors are locked — and fencing it would have been worse than useless, because the case it exists to diagnose is the one where the secret guarding it is what has gone missing.

Built, unproven
vercel.json

Frankfurt is load-bearing

Vercel executes functions in Washington DC for every new project unless told otherwise. Without regions: ["fra1"], the function that receives the passport upload runs in the United States — which defeats the entire reason the bucket and the database were pinned to the EU.

{ "regions": ["fra1"], "crons": [{ "path": "/api/cron/daily/", "schedule": "0 7 * * *" }] }

Keep that file free of commentary: Vercel validates it against a schema that rejects unknown properties, so a _comment key fails the build outright. That cost a deploy already.

Built, unproven
lib/storage/index.tsapp/api/cron/daily/route.tslib/admin/session.ts

Four deliberate ways to fail loudly

A half-configured deploy stops rather than misbehaving quietly. No R2_BUCKET in production and the app refuses to start — a deploy that silently discarded every ID scan while reporting success is the worse failure. No CRON_SECRET and the cron endpoint 401s everyone, Vercel included, because it sends mail to real customers. No ADMIN_SECRET and /admin cannot be signed into at all.

The fourth is the quiet one. Without APPLY_SECRET, every submission is refused with 401 — but the customer still gets their PDF, because the wizard falls back to the Phase 1 download. Nothing is recorded, and the office finds out from a missing row rather than from an error on screen.

One gap that is not a phase

No deletion job exists. Worth scheduling before the first hundred contracts rather than after.

Where to start

In this order. The first item unblocks everything else and takes a minute.

Push the 21 local commits Nothing can be previewed, reviewed or built by Vercel until origin has them. This is the single largest gap between the code and a release.
Run both suites locally pnpm install, then pnpm test for the 14 unit files, then pnpm db:up && pnpm test:db for the 17 database files. The db project is not parallelised — the suites share one database and truncate between tests.
Fix three stale claims in the docs The runbook asserts eight cars in three places and it is nine since yesterday; step 7 still tells the office that closing a rental is SQL; and DATA-RETENTION.md opens by saying retention is unsigned while its own body records the sign-off.
Set the Preview environment variables and deploy a preview Eleven new keys. Then hit /api/health first — it exists precisely so this step ends sooner.
Run the smoke test against the preview, not production Section 5 of docs/DEPLOY-PHASE-2-3.md: fleet endpoint, a 401 on the write fence, the browser gate, one real contract end to end, cron 401 and idempotency, then one real reminder email.
Warn the office before merging, not after From the merge, /apply/ needs ?k=. Every bare link already sent to a customer stops working and shows “Link nicht gültig”. Links that carry the key keep working.

The step most likely to go wrong

The real reminder email. It cannot be tested locally, SMTP from a serverless function has failed in this project before, and a sent email is the one thing in the whole runbook that does not roll back. It is last in the order for that reason, and it should go to your own address.
