TWINT payments from the email — how to start

TWINT emails us every time someone pays. The site will read those emails, work out which renter and which week each payment is for, and mark that week as paid. When it is not sure, it asks the office with one click.

1. What we are building, in one picture

TWINT email arrives→ Really from TWINT? (signature)→ Read the fields→ Find car, renter, week→ Two clues agree → week PAID

If the clues do not agree, the payment waits on a new admin screen, Zahlungen, with the reason in plain words and the most likely rental already selected.

The three clues
  • Reference: the customer's message names our car and a week, e.g. ZH 513 925 W3. Payment requests already ask renters to write exactly this.
  • Car + time: the message names our car, and we know who had that car at the minute of the payment. This uses the same rule as the traffic fines.
  • Payer: the email or phone TWINT shows belongs to one of our customers.
A payment is booked by itself only when reference + exact amount match, or car-and-time renter = payer + exact amount. One clue alone is never enough.

3. Your first hour

  1. Create a branch: 
    git checkout main
git pull
git checkout -b feat/twint-payments
  2. Read the two documents, in this order. They are the source of truth; this page only gets you started.
    • Design: docs/superpowers/specs/2026-10-12-twint-payments-design.md
    • Plan, task by task with code and tests: docs/superpowers/plans/2026-10-12-twint-payments.md
  3. Install the three mail libraries, pinned: 
    pnpm add imapflow@2.0.7 mailparser@3.9.28 mailauth@6.0.0
pnpm add -D @types/mailparser
  4. Add the mailbox login to .env.local (this file is git-ignored): 
    TWINT_IMAP_USER=info@zuriauto.ch
TWINT_IMAP_PASS=the-mailbox-password
  5. Create scripts/twint-peek.mjs from Task 0 of the plan, add "twint:peek": "node --env-file=.env.local scripts/twint-peek.mjs" to package.json, and run: 
    pnpm twint:peek
    It opens the mailbox read-only, prints each TWINT email's fields (payer names hidden) and ends with a summary.
  6. Answer the four gate questions from Task 0 and write the answers into the design document. Then start Task 1.
Stop and rethink if the summary shows emails that are not DKIM pass, or the field labels are different from Betrag, Transaktionsdatum, Transaktions-Nr., Name des Stores, Name, Kontakt, Nachricht. The whole design assumes both.

7. Rules that must not be broken

  • Open the mailbox read-only. Never mark, move or delete an email.
  • Never follow a link in a TWINT email. One of them refunds the payment.
  • No signature, no record. Only no-reply@twintpay.ch with a DKIM pass for twintpay.ch is read.
  • Never book on one clue. And never pay a different week because the named one is already paid.
  • No AI agent and no passwords in code or chat. The email is a fixed template; a plain parser is cheaper, testable and gives the same answer every time.

8. Useful commands

pnpm db:up                     # local Postgres in Docker
pnpm test                      # unit tests
pnpm test:db                   # database tests
pnpm twint:peek                # look at the real TWINT emails, read-only
pnpm twint:peek -- --html 1234 # raw HTML of one email, to save as an anonymised fixture
pnpm dev                       # run the site locally

# trigger the payment run locally (CRON_SECRET from .env.local)
curl -X POST -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/payments/

Most payments wait for reviewCustomers do not write the referenceDo Task 10 (pre-filled link); make Nachricht mandatory in the TWINT portal
Not in this version, on purpose: importing TWINT's portal export, handling refunds automatically, splitting one payment across several weeks. If the email route turns out too noisy, the sturdier option is a payment provider with webhooks (Stripe or Payrexx), where the reference cannot be edited by the customer.
